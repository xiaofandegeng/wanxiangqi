# 王者万象棋数据站：真实数据接入与 UI 改版开发任务书 v2

编写日期：2026-09-27。对象：接手开发的 AI、项目负责人、后续验收 AI。

本文件基于当前工作区代码和本次公开检索，覆盖数据获取、数据库、统计、页面改版及验收。它是开发任务书，不代表接口已经开通、数据已经获得或功能已经实现。当前工作区存在未提交修改，开发前应记录基线并保留用户已有工作。

## 1. 目标与交付边界

把当前依赖静态样例的展示原型，改为可持续更新、可追溯、可复算的数据产品。

必须完成四件事：

1. 数据由外部真实来源或经核验的真实材料进入后台，持久化到 PostgreSQL，再通过 API 展示。
2. 选手历史、登顶率、前三率、平均名次从有效对局记录计算；外部仅有汇总时，明确显示为来源方汇总。
3. 新增独立的阵容数据模块，接入可用且许可范围明确的官方或第三方数据，保留来源、版本和统计范围。
4. 页面改为克制、清晰的数据工具风格，移除夸张推演话术和缺乏依据的可信标识。

完成状态必须分开报告：

| 状态 | 定义 |
| --- | --- |
| 工程闭环完成 | 导入/采集 → 校验 → 数据库 → API → 页面 → 重启后仍可读取，全链路可验证 |
| 真实数据接入完成 | 至少一个来源的真实数据进入上述链路，提交来源及字段核对证据 |
| 持续同步完成 | 至少两次独立同步执行、幂等和失败恢复通过；数据源未变化时不伪造新增数据 |
| 选手战绩接入完成 | 有可关联到选手身份的真实逐局记录，或明确受限的真实汇总；不能用阵容大盘替代 |
| 预测可发布 | 另行通过数据时序与模型验证，不能因数据页面完成而自动开放 |

仅实现一个返回静态 JSON 的接口、把现有 mock 填进数据库、或有定时器但没有真实数据源，都不满足“真实动态接入”。没有官方接口不应阻塞 UI、数据库、导入和统计建设，但必须如实报告外部接入未完成。

## 3. 本次检索结论与接入选择

### 3.1 官方个人战绩：有查询入口，未确认第三方开放 API

王者万象棋官方账号发布的说明展示：战绩小助手支持个人总场次、夺冠率、前三场次，以及逐局时间、排名、棋手和英雄阵容；查询需要登录绑定游戏账号。公告没有证明第三方可以批量查询任意选手或导出全部历史。[官方功能说明](https://www.taptap.cn/moment/847173199970959963)

本次跟随公告入口，仅获取到绑定账号的工具引导页，其中还标有示例数据；未完成账号登录或真实战绩查询。不得把该引导页中的示例作为真实数据。[工具入口](https://www.taptap.cn/poster/NJQmumLSWj9P)

检索未发现足以支持直接实施的官方开放接口文档。这是“本次未确认”，不是断言接口不存在。官网及 `/ace/` 本次读取失败，不能据此判断网站停运或接口不可用。[官网入口](https://wxq.qq.com/)

接手 AI 的动作：先检查项目方是否已有正式授权接口、合作文档或本人导出材料。没有则保留 `OFFICIAL_API` 适配器能力声明为 `UNAVAILABLE`，不得猜测接口路径、伪造响应或要求用户提供游戏密码/Cookie。个人授权资料只能用于其实际授权范围，不自动涵盖其他选手。

### 3.2 第三方阵容统计：优先验证 hokace.wiki

本次可读取其阵容页，页面自称非官方资料库，标注快照 `v260917` 和 7 日窗口，提供阵容样本量、登顶率、前三率、平均名次及结构标识；页面也说明不同阵容结构可能共享对局，样本不能直接相加。它是可核对的外部统计候选，但本次未核实原始战绩、完整采样口径、更新 SLA 或再利用许可。[阵容数据页](https://hokace.wiki/zh/lineups/)

开发要求：优先核查它是否提供文档化 API、导出文件或允许的页面采集方式。记录允许使用的字段、频率、署名和缓存要求。确认可用后实现服务端适配器；不能因为页面能访问，就写成“官方实时全服数据”。未明确接入条件时提供来源链接，适配器保持待配置。

### 3.3 备选数据站与攻略站

`datawxq.com` 的检索摘要显示阵容、榜单和检索器能力；本次直接打开未提取到正文，未核实字段、统计口径、API、登录条件及使用许可。列为次优先探索项，不能承诺已接通。[万象棋大数据](https://www.datawxq.com/)

`wxqwiki.com` 有阵容攻略页面，可作为阵容命名和机制资料的候选；攻略条目、使用热度或作者评分不能自动当成对局胜率。[阵容攻略库](https://www.wxqwiki.com/lineups)

### 3.4 一个必须修正的数据解释

官方 9 月 24 日公告说明，支持阶段对比条以当前最高计数为基准显示。因此条形长度不能直接解释为六人总支持份额，更不能解释为胜率；公告同时确认可查看选手具体段位、观战与备战人数。[官方更新公告](https://www.taptap.cn/moment/851825583556921530)

产品字段必须区分 `relative_to_max`、`share_of_total` 和 `unknown`。只有精确计数已确认、分母完整且同一时点时，才能另算总份额。原始进度条永远不直接进入预测概率。

### 3.5 两条数据线独立推进

| 数据线 | 首选路径 | 无接口时可交付的路径 | 不能冒充的能力 |
| --- | --- | --- | --- |
| 选手个人战绩 | 正式官方接口或取得许可的逐局数据供应方 | 本人授权导出（若确有导出功能）、真实截图经 OCR 与人工确认、结构化人工录入 | 不能声称已覆盖任意选手、全服历史或自动同步 |
| 阵容环境统计 | 可用且许可明确的官方/第三方 API、导出或页面适配 | 有来源及时间的真实汇总导入，或只提供外链 | 不能反推每名选手的逐局战绩，也不能直接当成本场胜率 |

接入前形成来源登记表：来源地址、运营方、字段样例、授权依据、认证方式、模式/区服/版本覆盖、样本定义、时间窗、更新时间、请求频率、数据费用、可否缓存展示。没有资料的项写“未知”，不能由 AI 补全。

## 4. 实施顺序和架构

沿用 v1 的技术方向：Vue 3 + TypeScript + Pinia 前端，新增 Java/Spring Boot 业务后端与 PostgreSQL；开发时选择受支持的依赖版本并锁定。已有 Node watcher 保留为可选本机采集桥。不要为了改 UI 更换前端框架，也不需要先引入 Kafka、Redis 或独立模型服务。

若实施时仓库已新增真实后端，优先复用并更新本节决策，避免再造第二套业务服务。

```text
官方/第三方适配器 ──┐
真实文件导入 ──────┼→ 原始材料 → 解析候选 → 校验/人工复核 → PostgreSQL
本机截图采集 ──────┘                                      │
                                               统计查询/聚合 → 业务 API → Vue
                                                         │
                                                  已提交更新通知（SSE）
```

数据库是业务事实的持久化来源。SSE 只通知已提交的新版本，客户端按版本重新获取；断线重连通过 API 补齐，不依赖进程内 `lastCapturedData` 保存历史。

| 阶段 | 内容 | 退出条件 |
| --- | --- | --- |
| P0 纠正展示 + 来源探测 | 隔离 mock、撤下无证据指标；完成候选来源实测记录 | 真实页面为空时不填假数据；明确哪些来源可接、哪些待授权 |
| P1 持久化纵向闭环 | 迁移、后台、真实材料导入、API、选手与战绩基础页 | 一批真实材料经校对入库，重启后仍可查询，统计能手算复核 |
| P2 动态来源与阵容页 | 至少一个外部适配器、同步任务、失败处理、阵容统计页 | 真数据来源及持续同步证据齐全；外部阻塞单列，不伪报完成 |
| P3 全站 UI 整理 | 按本任务书逐页调整，补全空态、错误态、窄屏和筛选 | 主要流程可实际操作，截图与验收清单齐全 |
| P4 预测恢复（后续独立阶段） | 数据质量、时间回测、模型和结算验证 | 达成发布标准再启用；P1–P3 不以预测可用作为前提 |

先完成一个真实来源的全链路，再扩展更多适配器。不要同时搭多个空接口而没有任何数据落库。

## 5. 采集与导入协议

每个适配器分开声明 `player_identity`、`match_details`、`player_aggregate`、`lineup_aggregate` 能力，不能把只有阵容汇总的来源标成可获取个人战绩。

统一输出原始材料引用、来源记录 ID、原始字段、标准字段、解析器版本、问题列表及下一页游标。业务校验独立于解析器；API 或 HTML 结构发生变化时停止发布错误批次。

同步行为：

- 任务记录开始/结束、来源、游标、读取/新增/更新/重复/拒绝数量、错误和最后成功时间。
- 在数据库事务成功后推进游标；增量窗口带可配置回看范围以接收迟到和更正数据。
- 唯一键加 upsert 防重复；失败任务可重试；更正保存修订记录，不覆盖原始证据。
- 超时、429、403、解析失败分别处理；遵守来源频率和 `Retry-After`，有上限重试。403 不做绕过。
- 同步频率按来源实际更新节奏配置，不宣称秒级。`last_attempt_at`、`last_success_at` 与 `data_as_of` 分开。
- 上游失败保留最后有效快照并显示过期状态，不用 mock 顶替，也不把失败响应覆盖成空数据。

导入最小实现：CSV/JSON 上传 → 字段预览与行级错误 → 确认提交 → 返回批次 ID 与统计。提供带“仅测试”标签的模板，但真实验收使用可追溯材料。

截图流程：文件校验 → 保存原图和 SHA-256 → 实际 OCR → 字段及位置候选 → 人工确认 → 写入事实表。无 OCR 能力时提供人工录入，显示“待人工录入”；禁止根据文件大小猜名单。未知昵称不得自动匹配主播，不能将模糊识别标成 99% 可信。

本机采集桥仅在用户主动启用时工作，默认监听回环地址；禁止全来源 CORS 任意触发截屏。业务上传与审核接口应有身份校验、大小限制、文件类型检查；鉴权资料不进入前端包和日志。这里不要求开发自动下单或接管游戏账号。

## 6. 数据库调整

使用版本化迁移，保留现有有效表。先审查数据再迁移，不能用删除数据库重建的方式替代升级。演示数据使用独立数据库/独立 schema 或严格隔离的演示模式，默认生产查询不得读取。

### 6.1 事实、来源和汇总分层

| 表/实体 | 关键字段及职责 |
| --- | --- |
| `data_source` | 类型、来源地址、能力、许可记录、配置引用、同步频率、启用状态；不明文保存凭证 |
| `ingestion_run` | 来源、批次、幂等标识、游标、计数、状态、错误、开始/结束时间 |
| `raw_record` | 来源记录标识、内容哈希、原始 JSON/文件引用、抓取时间、解析器版本、批次 ID |
| `evidence` | 沿用原图存证，补材料所属来源与访问范围；哈希证明内容一致，不证明内容真实 |
| `player` + `player_external_identity` | 内部稳定 ID、平台、区服、外部来源 ID、确认状态；昵称历史独立记录 |
| `event` / 对局事实 | 模式、区服、赛季、版本、时间、参与人数、外部场次 ID、状态；区分王牌赛程和普通历史局 |
| `participant` / `match_history` | 逐选手名次、当时昵称/段位、棋手、英雄/等级/装备、原始记录和证据引用 |
| `lineup_definition` | 阵容结构、来源结构 ID、命名、分类器版本；未知阵容不强行套入旧六类 |
| `lineup_stat_snapshot` | 来源、阵容、模式、区服、版本、段位段、窗口、样本、登顶/前三率、平均名次、原始口径 |
| `player_stat_snapshot`（按需） | 聚合缓存或外部汇总；区分 `COMPUTED_FROM_MATCHES` 与 `PROVIDER_AGGREGATE` |
| `record_revision` / 审核记录 | 修订前后内容、操作者、原因、审核时间和所依据证据 |
| `forecast` / 评估运行 | 保留功能但默认不发布；保存输入快照、模型版本、数据截点、创建时间和有效状态 |

选手相关事实通用时间：`match_time`（比赛发生）、`observed_at`（材料观测）、`ingested_at`（系统收到）、`verified_at`（通过核验）、`available_at`（该修订首次可用于正式统计）。外部汇总另存 `window_start/end`、`data_as_of`。未知来源时间保留 null，不以当前时间伪造。

### 6.2 约束与迁移注意事项

- 外部选手键使用来源 + 平台/区服 + 外部玩家 ID，按来源真实身份域确定唯一性。直播平台、QQ/微信和游戏区服不能混用一个 `platform` 字段。
- 没有稳定 ID 时允许临时身份，显示“身份待确认”；同名不能直接合并，更名有可追溯映射。
- 来源去重键建议 `(source_id, source_match_id, source_player_id)`；跨来源同局合并要有明确映射，不能只用时间近似去重。
- 保留原始来源记录，但正式逐局统计只计一个规范化选手参赛事实，避免 `participant` 与 `match_history` 重复统计。
- 王牌六人约束只适用于已确认的对应模式；其他来源的参赛人数未知时不得硬改为六人。合法名次由对局规则校验。
- 限制席位数值为 1–6 不等于确保有六个席位；“发布完整结果”时检查人数、席位和名次完整性。异常并列按规则单独处理。
- 增补版本、模式、区服和时间窗索引；未知段位、倍率、来源胜率均可为空，不能补为 0 或常量。
- `event` 状态检查约束不等于合法状态迁移；服务层实现迁移规则、并发版本校验及审核权限。
- 将采集完整度、比赛生命周期、预测状态拆开；不应只有 `PREDICTABLE` 才能展示已核实的对局。
- 一场可有多次赛前预测，调整现有 `(event_id, model_version)` 唯一约束以保存不同截点；指定唯一发布版本，避免列表 JOIN 多模型重复场次。
- 阵容快照唯一性包含来源、结构、版本、范围和窗口；同名阵容跨来源不得直接当同一统计对象。

## 7. 统计口径

### 7.1 选手统计

默认展示“本站已收录记录”，不叫“全服完整战绩”。查询必须带模式、版本/赛季、时间窗与区服范围；跨版本汇总由用户明确选择。

对去重且审核有效、名次已知的 N 条记录：

```text
登顶率 = 第一名记录数 / N
前三率 = 名次 <= 3 的记录数 / N
平均名次 = 有效名次之和 / N
阵容使用率 = 归属于该阵容的有效记录数 / 阵容已识别的有效记录数
```

显示分子、分母和阵容识别覆盖数。未完赛或名次未知不进胜率分母，但应显示待补全记录数。N=0 时返回 null 并显示“暂无有效战绩”，不是 0%。近期 N 场先按条件筛选再按时间取最新 N 场，使用稳定次排序键。

区分两种情况：逐局计算结果可下钻到全部参与计算的记录；外部汇总只有来源方分母和窗口，不伪造对局明细，也不与本站逐局样本相加。总对局数未知时，覆盖率不能用“已收录 / 已收录”凑成 100%。

小样本只展示事实和数量。建议初始配置 N<20 标记“样本较少”，这是产品提示阈值，不代表 N>=20 就具备预测可靠性。

### 7.2 阵容统计

阵容页显示：核心英雄、棋手适用范围、样本量、登顶率、前三率、平均名次、来源、模式、版本、段位范围、数据窗口和更新时间。缺失项为“来源未提供”。不要把第三方综合评分当胜率。

默认同来源、同窗口内比较；不能把多个来源的百分比直接平均。只有能证明统计定义一致且样本不重叠时才考虑合并。只有四舍五入后的百分比时，不反推精确获胜次数。明确分母单位是整局、参赛记录还是来源定义的“样本”。

局后最终阵容属于结果信息，不能冒充赛前已选阵容。阵容的群体登顶率与特定玩家的登顶率、本场六人预测概率为三个不同指标。

### 7.3 时间安全与回测

赛前特征至少同时满足 `match_time < cutoff` 和 `available_at <= cutoff`；采用该截点时已存在且已确认的修订。今日补录的旧战绩不能回填昨日“当时已知”的预测；外部新发布的历史窗口统计同样受此限制。

预测快照不可被赛后数据覆盖；按场次和时间分训练/验证/测试集。现有 `v_model_evaluation` 只有冠军误差项，不能当完整 Brier 分数。完整定义：每场 `sum((p_i-y_i)^2)`，然后按场取平均；若用除以类别数的版本要另行标注。Log loss 为每场 `-ln(p_winner)`，并记录概率截断约定。均匀基线按该模式参赛人数计算。

P1–P3 默认关闭现有强推荐和预算建议；纯假设计算如保留，放入明确标记的实验页。预测恢复要求真实滚动回测、样本范围、校准与相对基线结果。结算状态只能由真实规则与原始到账材料验证；现有字符串签名不能开启功能。

## 8. API 与前端状态

以下路径是本项目待实现的内部接口设计，不是发现的官方接口。

| API | 用途 |
| --- | --- |
| `GET /api/v1/events?date=&mode=` | 指定时区日期的真实场次，返回采集状态与数据新鲜度 |
| `GET /api/v1/events/{id}` | 席位、赛前快照、已知结果、来源摘要；预测可为空 |
| `GET /api/v1/players?query=&mode=&sort=&cursor=` | 已收录选手分页检索，不预称全服天梯 |
| `GET /api/v1/players/{id}/stats?mode=&from=&to=&version=&limit=` | 明确筛选范围的统计及分母 |
| `GET /api/v1/players/{id}/matches?...&cursor=` | 同口径战绩下钻；默认每页 20 条，上限 100 |
| `GET /api/v1/lineups?source=&version=&mode=&minSamples=&sort=` | 外部阵容统计快照与分页 |
| `GET /api/v1/lineups/{id}?snapshotId=` | 固定快照详情，防止列表和详情窗口错位 |
| `GET /api/v1/data-status` | 各来源最后成功/尝试、数据时间、过期或失败状态 |
| `POST /api/v1/admin/imports` | 上传真实 CSV/JSON/截图并创建待处理任务 |
| `GET /api/v1/admin/imports/{id}` | 任务状态、候选、行级错误与导入统计 |
| `POST /api/v1/admin/imports/{id}/confirm` | 确认校对结果并幂等提交 |
| `POST /api/v1/admin/sources/{id}/sync` | 有权限地触发同步，返回任务 ID |

日期存 UTC，界面按 Asia/Shanghai 展示；日期过滤转换为该时区完整日区间。查询上限、排序字段白名单、null 排序、分页一致性需要明确实现。统计字段 API 用 0–1 比率，界面统一转换百分数。

响应元信息至少包含 `sourceId`、`dataAsOf`、`lastSyncedAt`、`sampleSize`、`scope`、`qualityStatus`、`warnings`；详细任务日志只给管理端。`qualityStatus` 区分已核验事实、来源方汇总、待核验、过期，不用一个“真实”布尔值概括全部。

前端区分加载中、空结果、来源未配置、缺身份权限、同步失败、历史快照过期。请求失败不展示假数据；可保留旧快照但附实际数据时间。筛选变化同步 URL，详情返回保留原筛选；避免较早请求覆盖较新的筛选结果。

## 9. UI 改版规范

### 9.1 方向与基础样式

目标是日常可读的数据站：信息表格优先、少量必要图表、来源和日期清楚。游戏感通过小尺寸角色图和榜单内容体现，不依赖霓虹、炫光和情绪化文案。

默认采用浅色：背景 `#F6F7F9`、表面 `#FFFFFF`、正文 `#1F2937`、辅助文字 `#667085`、边框 `#E4E7EC`，强调色 `#2563EB`。这些是本次设计建议，实施时检查实际对比度；暂不新增主题切换范围。

- 正文/表格 14px，辅助信息 12px，页标题 22–24px；数字使用等宽数字，数值右对齐。
- 内容宽度上限约 1280px，桌面左右留白 24px，手机 16px；区块间距 24px，圆角 6–8px。
- 不使用渐变文字、发光描边、循环雷达动画或全站玻璃背景。状态色仅表达状态，并附文字。
- 图表服务于真实历史：名次走势、名次分布、阵容表现对比；不用无依据的“战力雷达”和装饰性仪表盘。
- 保留键盘操作与清晰焦点，交互目标至少约 44px，动效尊重减少动态效果设置。

### 9.2 导航与各页职责

主导航：**对局 / 选手 / 阵容 / 历史记录**。数据来源与更新说明放在次级入口；采集核验与同步管理进入管理区。无实际结果时不把“模型与回测”作为主导航卖点。

| 页面 | 首屏内容 | 下钻/操作 | 移除或调整 |
| --- | --- | --- | --- |
| 今日对局 `/` | 日期、模式、已收录场次、更新时间；时间/状态/选手/结果表格 | 日期切换、场次详情 | 固定四场完整率、固定日期和“严格防泄漏”宣传条 |
| 对局详情 `/events/:id` | 场次信息 + 六席位对比：昵称、已核实段位、历史样本、登顶率、前三率、平均名次 | 查看选手、已收录历史、数据来源；赛后另区显示结果 | 六张重复营销卡、默认“最佳下注”、把历史偏好写成本局阵容 |
| 选手列表 `/roster` | 搜索、模式/区服/窗口筛选；昵称、样本、登顶率、前三率、平均名次 | 排序、分页、身份状态 | 没有全服榜单来源就改名“已收录选手”，不叫全服天梯 |
| 选手详情 `/players/:id` | 身份及范围、统计摘要、近期名次、逐局表 | 时间/版本/模式筛选、阵容偏好、来源详情 | 无记录时的默认战绩、主观“顶尖运营/绝对统治”评价 |

| 阵容详情 `/lineups/:id`（新增） | 结构、适用范围、统计窗口、各指标与来源 | 有数据才展示变体、装备或趋势 | 把攻略热度等同胜率 |
| 历史记录 `/archive` | 日期、模式、选手、结果、核验状态 | 查看完整对局与材料摘要 | 固定虚拟流水和未发生的收益 |
| 管理区 | 待校对、失败批次、来源状态、导入入口 | 原图与候选并排、确认/驳回、重试 | 前台满屏“审计通过”标签 |

### 9.3 文案替换与行为

| 当前风格 | 目标写法 |
| --- | --- |
| “深度自走棋沙盘推演”“秒级决策雷达” | “对局对比”“截图录入” |

## 11. 验收用例与证据

验收必须同时检查代码、数据库、接口和真实页面。下面的测试数字均是专用测试用例，不是真实玩家数据。

| 编号 | 操作 | 通过标准 |
| --- | --- | --- |
| A01 空库 | 启动真实模式，打开对局、选手、阵容页 | 显示各自真实空态，不出现固定玩家、胜率、审核完成或模型成绩 |
| A02 持久化 | 导入可追溯真实材料、确认，重启后端/前端 | 数据仍存在，可由 API 和页面查到，关联批次与原始材料 |
| A03 幂等 | 同一材料/来源记录重复导入两次 | 原始尝试可记录，但正式对局数与统计不翻倍 |

| A10 范围隔离 | 加入不同模式、版本和来源的战绩/汇总 | 筛选统计分母正确；第三方聚合不当作个人逐局记录 |
| A11 识别真实性 | 上传两张内容不同但大小接近的图，再上传无关图 | 不按大小返回相同预设；无关图明确失败或待人工录入 |

| A13 更正与回滚 | 修改一条已核实结果并审核，拒绝另一条错误记录 | 新统计与有效修订一致；旧材料和修改理由可查 |

| A16 展示状态 | 375px、768px、1440px；加载/空/失败/过期状态 | 无页面级横向溢出；信息可读、操作可达、无夸张虚假标签 |
| A17 数据分层 | 检查构建入口及生产查询路径 | 没有 mock 回退、生产假种子、文件特征伪 OCR、硬编码回测分数 |
| A18 模型（若恢复） | 手算六人完整概率向量的 Brier 与 Log loss，检查滚动数据切分 | 不是只算冠军项；预测发布时间与数据可用时间可核验 |

开发完成至少提供：

1. 实际改动文件和数据库迁移列表，API 文档与可执行启动说明。
2. 来源接入报告：每条来源的已实现能力、许可依据、字段样例、实测限制；不得将“候选”标成“完成”。
3. 一批真实材料的来源 → 原始记录 → 事实表 → 聚合 → API → 页面映射；只提交必要的脱敏证明，不泄露账号材料。
4. 测试命令及实际结果；至少运行前端 `npm run build`、`npm test`，后端相应测试、真实 PostgreSQL 迁移与统计集成测试。
5. 主要页面桌面/手机截图、关键交互检查记录，以及失败/空态截图。
6. 本节逐项状态：通过 / 不通过 / 外部阻塞 / 不适用（附理由），不能仅写“已自测”。
