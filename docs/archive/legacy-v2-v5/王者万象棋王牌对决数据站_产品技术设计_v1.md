# 王者万象棋王牌对决数据站 产品与技术设计 v1

> 调研日期：2026-09-27。供其他 AI 或开发者实施。目标是对“王牌对决·钻石狂潮”提供选手画像、赛前概率和钻石支持决策辅助。本文把已核实的公开信息、推断和待游戏内验证事项分开；示例数字均为演示数据。

## 1. 先读结论

最先实施的是 **数据可得性验证和结算规则核对**，而非直接接入第三方网页或训练模型。公开材料能够确认场次时段、六人选拔、简报结果、官方个人战绩工具和版本中的信息展示变化，但不能证明存在可供第三方批量使用的官方 API，也不能证明“返奖倍率”或支持钻石的结算公式。没有赛前快照与可核验结算，网站只展示历史数据，不输出钻石投入额或正期望收益结论。

## 2. 产品范围与硬门槛

首期仅覆盖王牌对决·钻石狂潮，移动端优先。展示赛程、每场六名选手、赛前段位及可得历史、预测第一名概率、样本数和数据新鲜度；赛后展示名次和赛前预测回测。支持录入游戏内截图，经人工校对后入库。投注建议只在结算与即时支持数据均核实后作为可关闭功能开放。网站不连接游戏账户、不代替玩家下单、不索取登录凭据。

**硬门槛 A：**至少连续 7 天记录每场赛前六人、开赛时间、最终六人名次、原图与采集时间，并计算完整率。**硬门槛 B：**核对支持规则及结算样本，确定是否只奖励第一名、支持收益是否随总投入变化、显示倍率是否含本金、是否存在限制。**硬门槛 C：**取得可合法持续使用的数据来源，或将人工录入作为正式运维方案。任何门槛未过，不实现自动钻石推荐。

## 3. 数据源调查与采集路线

| 来源 | 已知能力 | 未证实或限制 | 首期处理 |
| --- | --- | --- | --- |
| 游戏内对局列表与支持页 | 可见段位及支持阶段比较信息 | 能否看到稳定玩家 ID、准确支持金额、实时倍率和历史记录 | 人工截图，记录服务器时间与拍摄时间；OCR 后校对 |
| 游戏内简报和对局详情 | 公告称赛后发布对决结果 | 是否有完整六人名次、最终英雄阵容、可保存多少天 | 比对赛前截图和赛后截图，缺字段保留 NULL |
| 官方战绩小助手 | 自己登录后可看个人及对局数据 | 查询其他参赛选手的权限、导出与再利用许可 | 只用本人获授权数据做可行性验证，不共享凭据 |
| hokace.wiki | 公开阵容统计作概念与口径参照 | 采样偏差、更新频率、接口及转载授权 | 优先自行计算；合作前不批量采集或镜像 |
| datawxq.com 等第三方 | 检索结果表明存在对局检索页 | 数据来源、选手身份、可复用许可未核实 | 作为潜在线索，不作为 MVP 的依赖 |

采集流水线：截图上传 → 文件哈希去重 → OCR 给出候选字段及坐标 → 人工逐字段校验 → 保留原始证据和修订记录 → 生成赛前快照 → 赛后关联对局 → 校验六个名次、时间和版本 → 入统计。自动采集仅在取得明确授权、稳定标识与限频要求后新增适配器；不依赖客户端逆向、绕过认证或私有接口。

**现场验证清单：**准备同一局的选手确认、支持开始、中段、封盘、简报、详情、本人支持记录及到账记录截图；每张带时间。记录支持按钮是否允许多次、每次下限/上限、暂停和取消、赔率/回报是否锁定、并列或中止怎么结算、不同名次是否返钱、账户余额前后变化。至少对三场分别做一笔最小金额支持验证，手算到账与页面一致后签字确认公式。

## 4. 必备数据字典

每个字段存 `source_type`、`observed_at`、`captured_at`、`verified_at`、`evidence_id`、`confidence`、`game_version`；未知值为 NULL，不能填 0。

| 实体 | 必需字段 | 后续可选字段 |
| --- | --- | --- |
| event 场次 | id、mode、scheduled_at、status、version、采集时间 | 官方场次号、封盘时间、异常原因 |
| participant 参赛记录 | event_id、slot、player_id 或临时识别键、赛前昵称、段位原文、段位分、结果名次 | 备战/观战人数；外部页面链接 |
| player 玩家 | 内部 ID、平台/大区、可验证的官方稳定标识（若可获得） | 昵称历史、头像；昵称不能作为唯一键 |
| match_history 历史对局 | 对局 ID 或去重指纹、玩家、时间、模式、最终名次、数据来源 | 局内棋手、英雄及等级、装备、天赋、阵容结构 |
| support_snapshot | event_id、participant_id、observation_time、显示值及单位、规则版本 | 支持人数、支持总额、倍率、预估返奖；没有精确数值时仅存比较条比例 |
| wager 用户自愿录入 | 匿名本地或受控账户 ID、event_id、选手、投入、时间、显示条款、实际到账 | 结算截图；默认不公开个人记录 |
| forecast 预测 | event_id、模型版本、数据截止时间、六人概率、特征快照、是否为封盘前 | 置信区间、输出原因、暂停原因 |
| evidence 证据 | SHA-256、来源、采集时间、原图路径、审核人、审核状态 | OCR 原文、字段坐标、修订链 |

唯一约束：`event(mode, scheduled_at, platform)`、`participant(event_id, slot)`、经核验的 `match_history(source, source_match_id, player_id)`；所有版本化数值保留原始文本。赛前画像只从 `match_time < prediction_cutoff` 且当时已可获得的数据计算，杜绝结果泄漏。赛后最终阵容只能用于复盘和后续训练，不能回填该场赛前预测。

## 5. 指标口径与模型

- **选手登顶率** = 相同模式、最近 N 场中第一名次数 / 可验证对局数；**前三率** = 名次 ≤ 3 的次数 / 可验证对局数。展示样本量、时间窗、数据覆盖率、是否限于王牌场次。
- **擅长阵容**：先对最终英雄、局内棋手、核心结构定义一个可版本化的分类器；展示阵容使用次数、登顶率和同段位同版本的全局基准。若赛前无法得知本场阵容，阵容画像仅作为玩家历史偏好，不能称“本场使用阵容”。
- **平滑概率**：个体小样本以同模式、同段位群体先验收缩。例如 `(w + αp0)/(n + α)`，α 和时间衰减用历史数据回测确定。六人胜率不能直接相加当场概率；用六人相对强度模型归一化且总和应为 1。
- **基线预测**：优先 1/6 均匀模型；其后用赛前段位分、近期同模式名次、样本覆盖率做可解释模型（如 Plackett–Luce/条件逻辑回归）。手写权重只作实验，不能把未经校准 Softmax 称作真实概率。切换到更复杂模型需证明时间顺序回测优于均匀与段位基线。
- **回测**：按日期滚动训练与测试，禁止同一场拆入两侧。报告多分类 log loss、Brier、校准图、分段样本数、数据缺失率及相对基线提升；抽样偏差明显时暂停概率发布。

### 钻石计算（仅结算规则验证后启用）

设投入 `s`、选手第一名概率 `p`、若胜所得**总到账金额** `R_win(s, state)`、若负所得总到账 `R_lose(s, state)`，则 `EV_net = p × R_win + (1-p) × R_lose - s`；收益率 `EV_net / s`。若胜出还有多名次奖励，按各名次概率求和。任何显示倍率必须先确认它是“总到账/投入”还是“净收益/投入”，并记录结算时点与随支持池变化的函数。市场隐含概率 `1/m` 只在固定、含本金、单结果且无费的倍率模型下成立；动态分池不能照搬。支持池若会随下注变化，必须考虑本人投入对回报的影响。

投入上限首先遵守游戏上限与用户自设预算；概率误差、动态回报及仅四场/日使 Kelly 类最优比例极不稳定。MVP 的默认结果为“数据不足/不建议投入额”，后期也只给情景模拟、风险区间和最高预算，不给保本或稳赚承诺。网站的 ROI 仅以真实入账与真实支出计算；模拟 ROI 和实盘 ROI 分列。

## 6. 页面、接口与技术架构

页面：① 今日钻石狂潮（场次状态、时间、六人、段位、样本及预测）；② 单场对比（概率、数据截止、缺失、历史与封盘快照）；③ 玩家画像（昵称变更提示、模式分层、擅长阵容）；④ 历史对局及模型回测；⑤ 管理台（上传截图、OCR 校验、赛后核对、规则版本）。用户输入支持金额的模拟器在门槛 B 后开启。

建议沿用熟悉的 Java/Spring Boot 3 + PostgreSQL + Vue 3/TypeScript。文件原图对象存储；队列/任务服务用于 OCR 与日程；Python 服务可单独训练和发布模型版本。MVP 无需 Redis、Kafka 或复杂微服务，先保证时序证据与可追溯性。

建议只读接口：`GET /api/v1/events?date=&mode=DIAMOND`、`GET /events/{id}`、`GET /players/{id}/profile`、`GET /events/{id}/forecast`、`GET /models/{version}/evaluation`。管理接口：`POST /admin/evidence`、`POST /admin/events/{id}/participants`、`POST /admin/events/{id}/results`、`POST /admin/forecasts/{id}/publish`。管理接口鉴权、审计、限流；所有概率返回 `as_of`、`model_version`、`sample_size`、`coverage`、`status`。状态流：待收集 → 待校验 → 可预测 → 已封盘 → 已结算 → 已复核；撤销须保留审计历史。

## 7. 实施里程碑与验收

| 阶段 | 工作 | 完成标准 |
| --- | --- | --- |
| P0 规则与数据勘查 | 游戏内截图、结算复算、官方工具权限/条款调查、字段覆盖审计 | 一页经证据确认的结算公式；7天场次完整率与缺失字段报告；确定采集许可与负责人 |
| P1 手工数据 MVP | 数据库、截图 OCR 校对、六人场次与赛后简报、历史浏览 | 录入 7 天样本，字段有来源；六人名次一致；重复上传不产生重复场次 |
| P2 画像与基线 | 玩家身份匹配、模式分层统计、均匀与段位基线、时间回测 | 未知 ID 不错误合并；赛前查询不见赛后特征；模型报告含 log loss/Brier 与覆盖率 |
| P3 预测上线 | 可解释赛前概率、校准、异常暂停 | 六人概率和为 100%（允许显示四舍五入误差）；模型与截点可追溯；性能优于基线才发布 |
| P4 支持模拟 | 已核实的结算函数、场景模拟和预算约束 | 至少三笔人工结算逐项吻合；无法获得支持状态时自动隐藏建议；实盘与模拟隔离 |

最小样本说明：7 天用于验证采集链路，不足以宣称预测有效；建模需根据实际重复玩家、缺失率和分布决定扩大时长，不预设“几千场就足够”。2026-08-20 公告时段合计每天四场钻石狂潮，7 天理论最多 28 场，实际以游戏内为准。

## 8. 交给实施 AI 的首轮任务

1. 按本文 P0 做 `research/rules.md`、`research/source-audit.md` 与字段级 `research/data-availability.csv`；任何“API 可用”结论附授权说明与最小可复现证据。
2. 设计 PostgreSQL DDL 与迁移；提供匿名化样例 JSON、场次状态机、时序与去重规则，不生成虚构真实选手数据。
3. 做截图上传和人工校对原型、今日场次只读页面；先接样例数据适配器，再接真实数据源。
4. 编写以规则复算、时间泄漏、重复上传、错误身份合并为重点的测试；明确每一步验收证据。
5. 待用户提供真实游戏截图后填补规则空白；门槛 B 未过时，隐藏 EV/投入推荐并在 UI 显示“结算规则待核实”。

## 9. 待用户提供的最小材料

- 所在平台/大区和目前游戏版本；一场钻石狂潮从选手确认、支持、封盘到结算的截图或录屏，遮盖个人敏感信息。
- 游戏规则弹窗原文；至少三笔小额支持的投入、目标选手、支持时显示数值、结果、到账及时间（可分多天完成）。
- 赛后简报和某位参赛选手的战绩详情截图，确认是否有稳定 ID、历史阵容及名次。
- 网站计划仅自用还是公开发布；若公开发布，再确认图标、角色图和第三方数据的使用授权。
