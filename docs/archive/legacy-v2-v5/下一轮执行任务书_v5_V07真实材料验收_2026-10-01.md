## 1. 本轮目标

取得至少 5 条获准使用的真实个人逐局材料，在隔离验收环境完成：

**真实原件 → 身份绑定 → 候选导入 → 人工核验 → 数据库 → 统计复算 → API/页面对照。**

已有工程整改与定向回归已通过，不重新开发上传、版本管理、统计或浏览器工具。只修复真实验收中复现的阻断问题。个人批量 API、预测模型、扩大采集范围不属于本轮。

V07 通过只代表这批真实材料的人工接入链路通过；不代表完整个人历史、全服覆盖、预测准确或自动同步完成。

## 2. 开始前：真实材料门槛

先检查项目方是否已经提供材料，不能把 fixtures、之前隔离的数据、第三方阵容汇总或赛事积分榜拿来填补。

### 2.1 最小材料包

| 项目 | 要求 |
|---|---|
| 数量 | 至少 5 条不同的真实个人参赛记录，可来自一位或多位玩家；重复截图不重复计数 |
| 原件 | 原始截图或实际存在的官方/获准导出文件；不是手工填写的数字表 |
| 身份 | 能证明材料归属；UID、区服、平台等按实际可见内容记录，不凭昵称强行合并 |
| 逐局事实 | 对局时间、时区依据、模式、名次；多张原图可以共同证明一条记录 |
| 使用范围 | 明确允许内部验收还是公开展示；PUBLIC 不能由开发者自行选择 |
| 提供说明 | 提供人内部标识、获取途径、采集时间、允许保存/展示的范围；敏感材料不进公开仓库 |

优先最近连续 5 局，不刻意只选夺冠局；无法连续时记录选择方式和覆盖缺口。只有全赛季汇总不满足逐局材料要求。

使用已确认的官方个人查询入口时，由账号本人在其设备上登录操作。不要向用户索要密码或会话 Cookie，不猜测批量接口。

### 2.2 材料不足时的动作

- 可以检查环境、准备空核对表和执行命令，但不编造材料、不解封旧生成记录。
- 明确列出已收到多少条、哪些字段缺失、缺少何种授权。
- 少于 5 条可作阶段性验证，V07 仍标未完成。
- 提交“受阻说明＋待补材料清单”，结束本轮；不无限重复检索未确认的 API，不以等待时间视为授权。

## 3. 隔离环境与数据保护

1. 记录实际 HEAD、工作区状态、执行人、开始时间；保护现有未提交修改。
2. 使用专用测试数据库，例如 `wanxiangqi_v07_test`，及独立后端/前端端口。先确认连接目标，禁止把业务库当测试库。
3. 已有测试工具可能 DROP/重建 *_test 库。真实材料导入后，不要对承载这批材料的库执行重建工具；重建前必须确认可恢复备份及权限。
4. 使用真实材料时，即使库名为 *_test，也不能把原件、身份、访问令牌当公开测试夹具。原件及数据库备份放受控位置，不提交 Git。
5. 记录业务 storage.json 哈希和业务表计数；本轮默认不写业务库，不重启业务服务、不运行旧 seed 脚本。
6. 同步测试、错误注入和 fixtures 演练使用其他隔离库，不混入这批 V07 记录。

已有 browser-acceptance 工具会创建 FIXTURE 和重建测试环境；可借用其浏览器能力和操作方法，但不能把其演练结果或自动种子算入本轮真实材料。

## 4. 执行流程

### S1：材料盘点与身份确认

- 为每份材料分配 MAT 编号；记录受控存储引用、提供人、用途和材料中可确认的玩家身份。
- 建立玩家映射。现有 playerId 确认匹配后复用；没有可靠依据时保持临时身份或待确认，不能因为昵称相同自动合并。
- 缺少时间、模式或名次依据的记录先待补，不猜测。
- 参赛人数/名次按已确认模式规则处理；与当前支持范围不符时如实记录为受阻，不裁剪名次或改写模式来通过校验。

### S2：上传原件并确认材料有效

通过现有单人导入页 `/admin/personal-import`：

1. 配置隔离环境管理凭证。
2. 上传原件，选择实际允许的 usageScope；默认 INTERNAL_ONLY。
3. 下载或取回服务端原件，与本地文件比较字节数和 SHA256。
4. 确认上传只产生 PENDING；原图可预览、放大、读取。
5. 操作者阅读原件并确认归属、内容和用途，再执行材料核验。

不能通过直接 SQL 把证据或战绩改为 VERIFIED 来完成 V07。SQL 仅用于只读复核；人工填写一个哈希不等于上传原件。

### S3：逐局候选录入与核验

- 每局单独录入 playerId、matchTime、mode、finalRank 和 evidenceLocator。
- 原文没有的棋手、阵容、回合、天梯分保持 null。
- 同一图片包含多局时，材料内序号必须稳定、唯一；记录定位要能让另一人找到对应行。
- 提交候选后确认状态为 PENDING，再逐条对照原图核验。
- availableAt 使用系统实际核验时刻，禁止回填到比赛发生时间。
- 不为个人截图补齐其他五个席位，不创造缺失的对手记录。

### S4：按授权范围分别验证可见性

| 材料范围 | 应当可见 | 应当不可见 |
|---|---|---|
| INTERNAL_ONLY | 鉴权后的管理台账、原件及授权内部复核 | 匿名统计、逐局流水、赛事列表/详情中不得包含这些记录或其衍生结果 |
| PUBLIC | 获准展示的个人统计、逐局详情和页面 | 原件和敏感授权材料仍不得自动公开 |

**不要为了看到公开胜率，把 INTERNAL_ONLY 临时改成 PUBLIC。**

若全部材料仅限内部：通过管理端和只读 SQL 验证内部记录；公开 API/UI 正确排除它们同样是验收证据。报告写明“内部真实材料链路通过，公开真实样本尚无”，不能声称已经验证公开真实玩家统计。

若有 PUBLIC 材料：额外完成公开 SQL/API/UI 的同范围指标对照。内部与公开样本的分子、分母分别计算，不能混算。

当前没有管理端聚合统计接口时，不把公开接口改为读取内部数据。用管理记录集合独立复算；若业务明确需要内部统计页面，列为单独需求，不擅自扩大本轮。

### S5：独立复算

由核对者从原图直接读取数据，不能直接复制 API 数值当作正确答案。采用同一身份、模式、窗口、截止时刻与使用范围：

- N：本范围已核验且当前有效、去重后的参赛记录数量。
- W：名次为 1 的数量。
- T：名次 ≤ 3 的数量。
- R：名次总和。
- 登顶率 = W / N；前三率 = T / N；均名 = R / N。
- N=0 时比例与均名为 null；未夺冠但 N>0 时登顶率为 0。

复核数据库版本链，不能直接 COUNT(matches) 将 PENDING 和历史版本算入 N。优先复用已验证的可见版本口径，另以材料手算表作为独立参照；SQL 中记录全部筛选参数和时区。

### S6：幂等、历史截点与重启

- 同一批真实材料重复导入，当前有效计数不增加。
- 选择早于实际核验的历史截点，确认本批新核验记录未提前出现。
- 重启隔离服务，原件、身份、状态和统计一致。
- 错误更正、撤销等破坏性场景使用额外隔离副本或已有 fixtures，不能故意改坏真实材料库；真实记录确有错误时按版本流程修正并留痕。

### S7：针对真实链路的浏览器验收

不机械重跑全部五态 × 9 路由。重点执行本轮受影响流程：

- 上传、放大对照、材料确认、候选提交、逐条核验、刷新与台账核查。
- PUBLIC 样本：进入对应玩家页，筛选相同范围，核对指标和逐局记录。
- INTERNAL_ONLY 样本：管理端可见，匿名面不出现；新开无凭证会话验证，不只退出页面。
- 桌面与移动端确认关键操作可用，记录阻断错误与控制台异常。
- 截图包含个人信息时仅保存到受控目录；公开报告使用经允许的脱敏截图，避免遮挡本次要验证的关键字段。

若本轮修了代码，补针对性回归，再跑相关后端/前端测试及构建；未改代码且已通过的无关流程无需重复扩大测试。

## 6. 验收清单

| ID | 检查 | 通过标准 |
|---|---|---|
| R01 | 来源与用途 | 至少 5 条真实逐局记录，有可核对原件和明确用途；非 fixtures |
| R02 | 身份和字段 | 每条身份归属、时间、模式、名次均有材料依据 |
| R03 | 原件存证 | 服务端原件可恢复，字节数与哈希一致，访问受控 |
| R04 | 状态与时间 | 上传/导入不自动放行，实际核验产生新可见版本 |
| R05 | 授权边界 | INTERNAL_ONLY 对匿名面不泄漏；PUBLIC 仅按已获准范围展示 |
| R06 | 独立复算 | 原图手算、有效版本 SQL、相应 API/UI 口径一致 |
| R07 | 去重与持久化 | 重复导入不翻倍，重启不丢失，历史截点不回写 |
| R08 | 实际操作 | 浏览器完成真实材料流程，有受控证据；无阻断交互问题 |
| R09 | 隔离 | 业务库/业务文件未被验收改变；报告不泄漏原件或凭证 |

全部为内部材料时，R06 的公开部分应验证“被排除”，内部指标由管理记录和 SQL 复核；报告不得标注未执行的公开展示测试为通过。

- **自动同步：**仍未实现，除非另有正式接口文档、访问资格和独立验证，不以人工导入替代此结论。
