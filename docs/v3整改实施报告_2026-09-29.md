## 2. F04 根因专述

**现象**：整改前 `GET /api/v1/health` 返回 67 位玩家 / 1337 条战绩 / `PostgreSQL_Compatible_Local_Engine` / `EMPTY_COLD_START`，而 PG 实查 79/212。

**根因**：8080 服务进程于 9/28 由旧代码启动，其业务数据存活在**进程内存的 JSON 存储引擎**中（67/1337 为旧演示数据），从未落库；`EMPTY_COLD_START` 标记说明进程启动时未能从磁盘 JSON 恢复却照常对外服务。v2 存在三条互不同步的写路径（服务进程写 JSON、脚本直写文件+PG、测试重写文件），导致运行态、磁盘、PG 三处永久分叉。

**处置**：
1. 数据层：旧内存 67/1337 与库脱钩，**永久丢失于库外**——如实记录（`s4-old-8080-health-before-restart-20260929.json`），不伪造找回；
2. 代码层：删除 JSON 引擎路径，`backend/src/server.js` 重写为 pool→migrate→PgRepository→services 注入式 compose，formal 模式下 PG 不可用即拒绝启动，运行中断连 `/api/v1/ready`=503、写拒绝（V05）；
3. 验证：重启后 health counts 与 SQL 直查一致（`s8-final-health-20260929.json`：players 79 / matches 212 / effectiveMatches 0 / lineups 71），F04 闭环。

### 5.3 独立复算指引（任何人可对业务库直接执行）

```sql
-- ① 有效对局（应 = 0，与 health.effectiveMatches 一致）
SELECT count(*) FROM matches
WHERE verified AND record_status='ACTIVE' AND NOT synthetic
  AND final_rank BETWEEN 1 AND 6;

-- ② 对局状态分布（应 = 208 QUARANTINED + 4 PENDING，无 source_id）
SELECT source_id, record_status, count(*) FROM matches GROUP BY 1,2;

-- ③ 阵容快照按来源（应 = 36 datatft + 35 hokace）
SELECT source_id, count(*) FROM lineup_snapshots GROUP BY 1;

-- ④ hokace 存证（sha256 + 解析器版本 + 采集时间）
SELECT content_sha256, parser_version, content_type, fetched_at
FROM raw_materials WHERE source_id='src-hokace-wiki' ORDER BY fetched_at DESC LIMIT 1;

-- ⑤ 隔离备份完整性（249 整行可回滚）
SELECT count(*), min(sha256) IS NOT NULL FROM quarantine_backup_20260929141834;
```

对照 API：`GET :8080/api/v1/health`（counts 与 ①②③ 一致，F04 闭环）、`GET /api/v1/lineups`（与 ④⑤ 同源）、`GET /api/v1/players/:id/stats`（N=0 时比率全 null）。
